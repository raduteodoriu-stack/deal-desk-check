Card: `docs/cards/04_roadmap_cards.md` (the card file is the source of truth; keep this checklist in sync)
Depends on: DD-004, DD-014, DD-007

**Purpose:** compare what the contract says (DD-014 + DD-007) with the approved quote, the Opportunity and the Account, apply every C-rule in plain code, and return one outcome per deal (PASS / REVIEW / BLOCK) with a finding for every difference, each showing expected, found and the contract text that proves it.

**Story:** Finance shouldn't have to re-read a contract to trust a booking. The comparator does the line-by-line check a careful analyst would do (same customer, same SKUs, same amounts per year, same terms that were approved) and writes down every difference in a form Finance can act on: "C-08: CRD credits year 3, expected €170,000.00, found €180,000.00, with the order-form line quoted". Code decides; a person still books, and can clear a REVIEW or BLOCK only with a reason code.

**Inputs:** `contract_extraction/v1.2` (pre-check values, with LLM values filling only the gaps), `precheck_report.json` (flags: missing pages, missing clauses, injection), `quote.json` with its approvals, `opportunity.json` and `account.json` (DD-003), and DD-004's recomputed ARR / ACV / TCV. Every threshold comes from `contract_checks` in `rules/deal_desk_rules_v1.4.json`; nothing is typed into code.

## Decisions (each with options, trade-offs and a recommendation; awaiting owner decision)

### 1. What "expected" means for terms that can be approved (C-11 to C-16, C-23)
| Option | How it works | Trade-offs |
|---|---|---|
| **A. The approved quote terms if an approval is recorded on the quote; otherwise the standard term from the rules (recommended)** | For each term, look for an approved non-standard term (N-rule, approver, value) on the quote. If there is one, that value is expected. If not, the standard value or band from `standard_terms` is expected | Approved exceptions pass, unapproved ones block, and a contract that is *more* standard than approved is caught too. Needs the quote to carry the approved values, which DD-003 and DD-004 already provide |
| B. Always the standard term | Any non-standard term in the contract is a finding | Simple, but every approved exception would block (DL-03 would fail), so people learn to ignore the check |
| C. Whatever the playbook allows | Any allowed variant passes, approved or not | Lets an allowed-but-not-approved variant through (e.g. a Net 45 nobody signed off) |

*Example:* DL-03 has Net 45 approved under N-01 by Finance. The contract says 45 days, so C-11 passes. DL-08 has Net 30 approved and the contract says 60 days, so C-11 is BLOCK with expected 30, found 60. If a contract said Net 15 against an approved Net 30, that is better for MoP, so C-11 is REVIEW (the JSON's `better_for_mop`), not BLOCK.

### 2. How detailed a finding is
| Option | Trade-offs |
|---|---|
| **A. One finding per rule per compared item (a field, or a line item and year), each with expected, found, page and snippet (recommended)** | Finance sees exactly which line and year is wrong, and DD-005 gets one `Contract_Check_Finding__c` row per difference. A single error can produce a few rows |
| B. One finding per rule | Short list, but "C-08 failed" doesn't say which of 9 line-years is wrong |
| C. One finding per contract clause | Matches how Legal reads, but money rules (C-08, C-10) don't map to one clause |

*Example (DL-05):* `C-08 | CRD-ENT year 3 net | expected 170,000.00 | found 180,000.00 | page <n> | "Year 3 ... €180,000.00"`. Years 1 and 2 match, so they produce no finding. Passed checks are counted in the summary, not listed one by one.

### 3. When one error makes other rules fail too (derived rules)
| Option | Trade-offs |
|---|---|
| **A. Report every rule that fails, and tag a finding with `follows_from` when it is a known knock-on of another finding in the same run (recommended)** | Honest: nothing is hidden, and the outcome can't be understated. The tag tells the reviewer where to start. It matches the DD-003 answer key, which lists primary + derived rules |
| B. Report only the root cause | Shortest list, but the code then guesses which failure is "the real one", and a guess that's wrong hides a real problem |
| C. Report everything with no links | Complete, but the reviewer has to work out the chain alone |

*Example (DL-06):* the contract says 500,000 credits instead of 50,000. Findings: C-09 (credits per year), C-08 (the credits line net amount) tagged `follows_from: C-09`, and C-10 (ARR and TCV no longer match the Opportunity) tagged `follows_from: C-08`. The known links are fixed in code and few: C-09 → C-08, C-08 → C-10, C-05 → C-06, C-20 → C-19.

### 4. A field the rule needs is empty
| Option | Trade-offs |
|---|---|
| **A. The rule is marked `not_evaluable` and C-19 REVIEW is raised for the missing field. Exception: if the document is complete and a required clause is simply absent, the rule judges the absence (recommended)** | Never guesses and never passes on missing data; a person looks. The exception keeps a deleted clause a BLOCK instead of softening it to REVIEW |
| B. Treat a missing value as a mismatch (BLOCK) | Strict, but a missing page would show as a wall of false BLOCKs on rules that may be fine |
| C. Skip the rule | Quiet, and lets a deal PASS without checking it. Not acceptable |

*Example:* DL-14 is missing page 4. Every field on that page (for example the uplift cap, CL-UPL-01, in DD-006's layout) becomes empty, so C-14 and any other rule that needs it are `not_evaluable`. C-19 is raised for each missing field and C-20 for the page, so the outcome is REVIEW (matching the key: C-20 + C-19). DL-09 has all 6 pages but no auto-renewal clause, so C-13 judges the absence against the standard and returns BLOCK.

### 5. Matching the customer's legal name (C-02) and VAT ID (C-03)
| Option | Trade-offs |
|---|---|
| **A. Normalise both sides (case, accents, punctuation, spaces, the legal-form suffixes listed in the JSON), then: equal → pass; similarity ≥ 0.90 → REVIEW; below → BLOCK. VAT IDs: normalise (remove spaces, dots and dashes, uppercase the country prefix), then exact match only (recommended)** | Ignores harmless formatting, sends typos to a person, blocks a different company. Similarity uses Python's standard `difflib` ratio, so there is no extra library, and the score is shown in the finding. A VAT ID has no "nearly right" |
| B. Exact match only, no normalisation | Predictable, but "S.L." vs "SL" would block |
| C. Fuzzy pass at ≥ 0.95 | Fewer reviews, but a one-letter difference between two real companies would pass |

*Example:* "Laboratorio Ficticio Tajo, S.L." vs "LABORATORIO FICTICIO TAJO SL" → equal after normalisation → pass. "Laboratorio Fictcio Tajo S.L." (a typo) → similarity about 0.97 → REVIEW. A contract signed by the parent "Grupo Tajo Holding S.A." for the subsidiary's Account → similarity well under 0.90 → BLOCK. VAT `ES B12345678` vs `ESB12345687` → normalised, different → BLOCK (DL-07).

### 6. Which quarter C-22 compares
| Option | Trade-offs |
|---|---|
| **A. Calendar quarters (MoP Cloud's fiscal year = calendar year), stated as an assumption in this card (recommended)** | No rules change needed, and it's what most small SaaS companies use. If MoP Cloud ever has a different fiscal year, that is a versioned rules change |
| B. Add `fiscal_year_start_month` to the rules JSON now | Ready for any fiscal year, but it is a rules change (v1.5) for a value nobody needs yet |
| C. Any difference in dates → BLOCK | Simple, but blocks harmless cases the rules define as REVIEW |

*Example:* signed 2 January 2027, Opportunity closed 31 December 2026 → different quarters → BLOCK (revenue would land in the wrong quarter). Signed 15 March, closed 10 March, same year → same Q1 → REVIEW, so someone corrects the close date.

### 7. What DD-005 receives
| Option | Trade-offs |
|---|---|
| **A. Two CSVs per run, `contract_checks.csv` and `contract_check_findings.csv`, linked by a key `Check_Key__c` = deal ID + run ID; each finding also has `Finding_Key__c` = check key + rule + item (recommended)** | Data Loader or the Import Wizard can upsert both objects and link children to parents by the key. Re-importing the same run updates rows instead of duplicating them (the DD-009 "no duplicate findings on re-run" test). Needs 2 External ID fields added to DD-005 A |
| B. One flat CSV with check and finding columns together | One file, but the check columns repeat on every row and Salesforce can't load two objects from one file without extra steps |
| C. JSON pushed through the Salesforce API | Closest to production, but needs a connected app and credentials in the MVP; that belongs to DD-009 (n8n) |

DL-08-R001-C-11-payment_terms_days,DL-08-R001,C-11,BLOCK,30,60,"p2: Payment is due within 60 days of the invoice date."

## Also fixed (no options needed)
| Topic | Decided |
|---|---|
| Outcome | `outcome_precedence` from the JSON: any BLOCK → BLOCK; else any REVIEW → REVIEW; else PASS. A person still books, and clears with one of the 5 DD-002 reason codes |
| Money | `Decimal`, never float. Tolerance €1.00 (`money_tolerance_eur`) per compared amount: each line and year for C-08, ARR_1 and TCV for C-10. Bonus credits never counted in ARR or TCV (C-23) |
| Confidence | Any value with confidence under 0.80 (`extraction_confidence_min`) or an unverified snippet → C-19 REVIEW |
| Routing | C-17 findings carry `route_to: Legal`; C-21 carries `security_flag: true`, and the other rules still run on that contract |
| C-18 | Quote number and version must match the approved quote, and the approval must be valid on the last signature date |
| C-20 | MVP checks page sequence only (no PDF text layer yet) |
| Pre-check vs LLM | The pre-check value wins. If both stages report different values for the same field, that is a C-19 REVIEW (guard; should never happen by design) |
| One rule, one function | Each C-rule is a pure function `check_c08(contract, quote, ...) -> list[Finding]`, with no file or network access, so each can be tested alone |
| Stamped | Every result carries `rules_version`, `template_version`, `playbook_version`, `prompt_version` and a run ID |

## How it works (per deal)
1. Load the bundle, the merged extraction, the pre-check flags and the rules.
2. Normalise names, IDs, dates and money.
3. Build the expected terms: approved quote terms where an approval exists, the standard otherwise (decision 1).
4. Run C-01 to C-23; each returns findings or `not_evaluable`.
5. Raise C-19 for every `not_evaluable` field and every low-confidence or unverified value.
6. Tag known knock-ons with `follows_from`.
7. Apply precedence and write the JSON result and the two CSVs.

## Acceptance criteria
- [ ] Every C-rule is a pure function with its own tests, including the rules no deal plants (C-01, C-02, C-04, C-07, C-12, C-16, C-22, C-23): at least one pass and one fail case each
- [ ] All thresholds and suffixes are read from `contract_checks` in the rules JSON; a test changes the tolerance and the result changes
- [ ] Clean deals DL-01, DL-02, DL-03 → PASS, including DL-03's approved Net 45 and 4% uplift cap
- [ ] Each error deal DL-04 to DL-15 returns the outcome and the failed-rule set in `answer_keys.csv` (primary + derived), with `follows_from` on the derived findings
- [ ] DL-14: missing-page fields are `not_evaluable` with C-19, never guessed; DL-09's absent clause is judged (C-13 BLOCK)
- [ ] DL-15: C-21 with the security flag, and every other rule still evaluated with unchanged values
- [ ] C-02 cases: suffix-only difference passes, typo → REVIEW, parent company → BLOCK; C-22 cases: different quarter → BLOCK, same quarter → REVIEW
- [ ] `contract_checks.csv` and `contract_check_findings.csv` match the DD-005 field names; running the same run twice gives identical keys
- [ ] `docs/test_report.md`: precision and recall per C-rule and overall; K-09 = 100%, K-10 ≤ 10% (with 3 clean deals, that means 0 false blocks), K-11 reported; any miss explained
- [ ] `pytest -q` passes offline, with no network calls
